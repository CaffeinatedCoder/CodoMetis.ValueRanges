# CodoMetis.ValueRanges

This file is the canonical agent guide. `CLAUDE.md` only imports it (`@AGENTS.md`), so Claude Code
and every other agent read the same rules. Edit this file, never `CLAUDE.md`.

In-memory range and multirange types for .NET 11 on `main` (the 11 line; `release/10.x` stays on .NET 10), mirroring PostgreSQL's six built-in range domains (`int4range`, `int8range`, `numrange`, `daterange`, `tsrange`, `tstzrange`) plus two v5 additions: `TimeRange` over `TimeOnly` (maps to the custom `timerange` type — needs `HasPostgresRange` + `EnableUnmappedTypes` on the EF side) and, in the NodaTime satellite, `YearMonthRange` over `YearMonth` (stored as a month-aligned `daterange`). Since 10.0.0, `Float64Range` and `Float32Range` cover finite `double` and `float` (the custom `float8range` and `float4range`, set up like `timerange`), with `Float64Set`/`Float32Set` and their arities on `double precision[]`/`real[]`. Each range type is a discriminated union of five sealed variants with exhaustive pattern matching.

Since v6 there is a second type family: **value sets** (`Sets/`) — immutable, canonical (deduplicated, sorted, no nulls) sets of scalar values stored as native PostgreSQL arrays (`StringSet`/`text[]`, `GuidSet`/`uuid[]`, …), plus a validated-wrapper arity for every family (`StringSet<T>` … `DateTimeOffsetSet<T>`, and five more in the NodaTime satellite) constrained only on BCL interfaces. EF maps them as scalars with plugin-owned mappings and translators (`@>`, `&&`, `<@`, `cardinality`, `array_remove`) — never through EF's primitive-collection machinery. Since 10.4.0 `Union`, `Add`, `Intersect` and `Except` run as one canonicalizing subquery (`ARRAY((SELECT DISTINCT ON (x) x FROM unnest(…) WITH ORDINALITY … ORDER BY x, ordinality))`) for every family whose order PostgreSQL shares (`ISetTypeDefinition.CanonicalizesInSql`, #478), built by the SQL guard. Only text is left out: `ORDER BY` follows the database collation rather than ordinal order, so on `StringSet`/`StringSet<T>` `Union` stays `array_cat` and `Intersect`/`Except`/`Add` stay client-side only until #479 decides the order (`docs/efcore.md#what-runs-where`).

## Stack
.NET 11 (`main`; `release/10.x` is .NET 10) · C# 14 (extension methods) · MSTest 4.x · EF Core 11 + Npgsql (PostgreSQL bridge)

## Workflow
1. Read `docs/architecture.md` before modifying range types or interfaces
2. Explore the codebase — range operations are per-shape (Finite, UnboundedStart, etc.)
3. Run `dotnet test` after each change; tests are method-level parallel
4. **Prove every fix by reverting it.** Strip only the fix, confirm the new test fails for the
   expected reason, restore. A test that passes with and without the fix is not a regression
   test — and one written against broken code can assert nothing at all without looking any
   different. The same applies to a new convention test: seed the defect it claims to catch. For an
   oracle sweep, keep the revert as `test/oracles/seeds/<defect>.patch` naming the oracles it fails
   (`OracleSeedTests` requires one per registered oracle), and run `dotnet run tools/oracles.cs
   seeds` before a release
6. **Finding bugs is systematic, not one-off.** Start from `dotnet run tools/oracles.cs status`: an
   unheld claim or an unwaived public member is the next oracle to write, and a new sweep goes into
   `oracles.json` with a seed. A new public member fails `OracleSurfaceCoverageTests` until a claim
   names it or `surface-waivers.json` says why none should; a reworded doc sentence fails
   `OracleCatalogueTests` until its claim follows. A disagreement a sweep finds goes through
   `Candidates.Verdict` into `candidates.json` with its issue, never into an `Assert.Inconclusive`
   or a deleted row; the entry fails as `candidate fixed` once the defect is gone. A fix commit
   carries `Found-By:` and `Defect-Class:` trailers (CONTRIBUTING.md)
5. Commit with conventional format: `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `build:`

## Issues
Work is tracked as GitHub issues, not as lists in docs or memory. Open the issue before starting
the work, and close it from the PR (`Closes #n`).

- **Labels, on issues and PRs alike** (the EntglDb/BLite scheme): exactly one type (`bug`,
  `enhancement`, `documentation`, `tests`, `chore`); every `package/*` the change affects
  (`core`, `nodatime`, `efcore`, `efcore-nodatime`); the `area/*` concern (`ranges`, `range-set`,
  `value-sets`, `json`, `literals`, `aot`, `release`); and `severity/*` on a bug. Add `silent` to
  a bug that answers wrongly without throwing. Its fix went in the next major up to 10.0.0;
  after 10.0.0 it ships as a minor on every supported line (never a patch), whose changelog entry
  opens with `### Changed answers`, a row linking the issue and its `docs/migration.md` section
  (`pr-hygiene.sh` fails a `silent` PR into a minor without that row). Add `breaking` to anything that changes an existing answer or
  signature, `found-by/oracle` to what the generated-oracle machinery finds, and `stacked` to a
  PR whose base is another open PR
- **PRs** carry their issue's labels and milestone, open with `Closes #n`, and describe the
  problem, the change and how it was verified
- **Epics:** a release is an `epic` issue with a milestone of the same version (`9.1.0`). Its work
  is attached as native sub-issues and carries the same milestone. A theme that spans releases is
  an `epic` without a milestone; a finding it produces belongs to the release epic it ships in
- **Roadmap:** the pinned `roadmap` issue (#34) holds every epic as a sub-issue
- **Discussions** (Q&A and Ideas) explore questions and directions and never hold state. An
  accepted idea becomes an issue, the discussion links it, and status lives on the issue and its

- **Branches:** up to two lines are supported at once, 10.x (LTS, .NET 10) and 11.x (.NET 11).
  Until the `v10.0.0` tag: `main` is 10.0.0, and `release/9.x` holds 9.x patches and then takes no

## Critical Rules
- **NEVER** create external subtypes of range base records — the private constructor is what makes the five variants the only ranges that can exist, so a switch over them is complete *in fact*. C# never proved it (exhaustiveness analysis ignores a closed class hierarchy, so a switch expression still warns CS8509 and needs a throwing discard — see `docs/ranges.md#pattern-matching`), which is exactly why breaking the rule is unrecoverable: the guarantee is entirely a runtime one, and nothing would fail at compile time
- **ALWAYS** preserve RangeSet's invariant (sorted, disjoint, non-adjacent, no empties) on every code path that constructs or mutates a set
- **Do NOT** add new range types without verifying the generic engines cover them — a new type must implement `IRange<T>` + `IRangeFactory<TRange, T>` with the five sealed variants; the engines in `Internals/` dispatch per shape through the structural interfaces. The procedure is `docs/architecture.md#adding-a-range-or-set-type`: measure the domain on a live server, copy the nearest sibling on every axis, and let the discovered tests and the clone sweep list what is left — there is deliberately no template or scaffold
- **Ranges — NEVER decide a binary operation by switching on the receiver's shape.** A binary relation is a function of the *pair* of shapes: read the bounds it actually compares, or switch on `(left, right)`. Switching on the receiver and handling the operand's shapes in an inner switch has now produced the same bug four times — `IsAdjacentTo` (fixed 6.2.1), `IsStrictlyLeftOf` and `Except` (both 7.0.0), and `RangeSet.Except(TRange)` with an infinity operand (8.0.0). The tell is an inner switch with a `_` fallback: it answers `false`, or returns the receiver unchanged, for exactly the operand shapes nobody wrote an arm for. **This applies to value-producing operations, not just predicates** — `Except` returned a well-formed range holding the wrong values, which is the harder one to notice. It hides well because the EF translation is correct, so the disagreement is between memory and the database rather than inside either. `ShapeMatrixParityTests` asks PostgreSQL for every ordered shape pair and is the check that catches it
- **Ranges — a shape dispatch's `_` arm MUST throw, never produce a value.** C# cannot prove a switch over interface patterns exhaustive, so the discard arm cannot be removed — the point is that it stops answering. Since 8.0.0 the three engines have one entry point each taking `IRange<T>` on both sides, switch over `(left, right)` with one arm per accepted pair, and throw `ShapePair.Unreachable` naming the pair for the rest, so an unhandled pair is a missing *line* and a loud failure rather than a plausible value. `EngineDispatchConventionTests` parses `src/**/Internals/` and enforces both halves — throwing discards, and entry points that are not typed by one operand's shape
- **JSON and TypeConverter — every range union, every sealed variant, `RangeSet` and every value set type MUST carry its own `[JsonConverter]` and `[TypeConverter]`.** For `[TypeConverter]` the variant trap is reversed: it *is* inherited, so a variant without its own silently uses the union's and answers with whatever shape the literal has; `TypeConverterContractTests` catches that. Since 9.0.0 the literal is the wire form with nothing registered. System.Text.Json does not inherit the attribute, and a value reached through `object` is handed over as its *variant* — an attribute on the union alone silently leaves those on the `{"Length":…}` property dump. Non-generic types name a closed converter (source-generation friendly); generic ones name `RangeJsonConverterFactory`, because an attribute cannot name an open generic converter. `JsonDefaultContractTests` discovers every type and fails on a missing one. The range and set interfaces carry `InterfaceDeclaredJsonConverter` (write through the runtime type, refuse a read), and a variant converter defers to a union converter registered on the options — both so a value's wire form never depends on how it was declared
- **AOT — a generic range set or value set type MUST register its own closed converters** (`internal static readonly bool ConvertersRegistered = GenericConverters.Register(…)`), and nothing may build a converter with `MakeGenericType`. Under Native AOT an instantiation over a value type that no compiled code creates does not exist, and whether one does depends on unrelated code — an AOT test can pass by accident. Both libraries build with `IsAotCompatible`; the NativeAOT consumer in `test/consumer-smoke-test.sh` is the only check that code is actually compiled (seed a defect there, not in a unit test)
- **Literals — NEVER let an `IFormatProvider` reach the literal.** `Parse`/`TryParse` read the invariant literal and ignore the provider; formatting without a format string is the invariant literal whatever the provider (a provider applies only with an explicit format). Before 9.0.0, `th-TH` parsed `2026-01-01` as Gregorian 1483 and `de-DE` turned `$"{DecimalRange [1.5,2)}"` into `[1,5,2)` → `[1,52)`, silently. `LiteralProviderContractTests` and `LiteralCultureContractTests` sweep every type under five cultures
- **Literals — temporal element text is strict ISO 8601, NEVER a lenient BCL `Parse`.** `IsoTemporal` (BCL) and `NodaPatterns` (NodaTime) accept exactly what this library writes and what PostgreSQL prints in ISO `DateStyle` — space separator, `+05` / `+05:30` / `±HH:mm:ss` offsets, `infinity` / `-infinity` as the extremes — plus `HH:mm`. A `DateTime` offset is accepted and **never applied** — the wall clock is kept, as `Local`, which is PostgreSQL's `timestamp` input rule; converting it made one literal a different `tsrange` value on every machine. Before 9.0.0 `DateOnly.Parse(invariant)` read `[01.02.2027,05.03.2027)` month first and an offset-less `DateTimeOffset` took the machine's offset, silently. A wrapper arity parses as its primitive first and hands the element its round-trip form, and a closed temporal set reads its JSON elements through the same grammar whenever System.Text.Json's built-in converter would have (a registered converter still wins). `TemporalLiteralStrictnessContractTests` refuses a non-ISO element through every entry point of every discovered temporal type
- **EF Core**: new range types are wired exclusively through `RangeTypeRegistry.Register` (satellites call it from their options-builder extension); never bypass the registry
- **EF Core — a translator maps an operand from the type its overload declares, and throws `MissingArm` for any other.** So does the interceptor's `RangeSetContains.Equivalent`, which picks the static form of a `RangeSet.Contains` overload by its operand type (#320). The translators recognize an overload by its name, and `RangeSet` calls mapped every operand that was neither the set nor the element as a range, so an overload added later with another operand type would have become a range operator over the wrong mapping, without an error (#295) — the receiver-shaped dispatch trap one layer up. Declining is not enough: EF Core's own translators match by name too, as its collection `Contains` took `RangeSet.Contains` (#288). `TranslatorDispatchSweepTests` hands every public overload to the translators, so a new one without an arm fails there first
- **EF Core — NEVER replace, register or derive from `IMigrationsModelDiffer` or `IMigrationsSqlGenerator`.** EF resolves each as a single service, so when two packages replace one the last registration wins and the other's migration DDL disappears without an error. From 11.0.0 on, `CodoMetis.EFCore.SchemaKit` owns both in the CodoMetis family: a migration-aware feature goes into SchemaKit or plugs into its contract, never into a replacement here. The custom store types (`timerange`, `float8range`, `float4range`) are created through Npgsql's `HasPostgresRange`, which needs neither. `MigrationServiceOwnershipConventionTests` fails on a shipping type implementing either service and on any reference to them in code under `src/` (`ReplaceService`, `TryAdd`, `ServiceDescriptor`, a base list); comments may name them
- **EF Core — a temporal value written as text MUST be the value Npgsql would bind.** A JSON document and a SQL literal hold the microsecond truncated toward 2000-01-01 (`StoreTemporal` / `NodaStoreTemporal`, passed as a definition's `storeValue` — never folded into `normalizeValue`, which must stay the core's `NormalizeElement`) and spell the extremes Npgsql maps as `-infinity` / `infinity`; ranges are rebuilt through their factory afterwards and sets deduplicated. PostgreSQL's text input rounds half-to-even, so seven fraction digits make a document or constant a different value from the column. The JSON writer resolves its store text through the registries (`StoreText<T>`), never from state a definition's constructor set — a compiled model may never build a wrapper family's definition. `TemporalStoreParityTests` (integration) is the authority
- **EF Core — an inlined range constant arrives typed as its sealed variant.** EF evaluates a range built from query-independent values on the client and inlines it as `Constant(value, Int32Range.Finite)`, for which no mapping exists; `RangeVariantConstantRetyper` in the query interceptor retypes it to the union. Do not "fix" this by mapping the variant types — that would make variant-typed properties mappable
- **EF Core — a constant element operand must be typed.** The range operators are polymorphic (`anyrange @> anyelement`) and PostgreSQL resolves those without implicit coercions, so a bare numeric literal (which it types as `integer`) does not match `int8range`. Assert the whole operand in translation tests, never the `@> ` prefix, and execute at least one constant-operand query per element type against a live server
- **Value sets — ALWAYS** preserve canonical form (deduplicated, sorted by the family's canonical comparer, no nulls) on every construction path, including reads. String-backed families sort **ordinal** — never culture, never the element's own `IComparable`
- **Value sets — NEVER** implement `IEnumerable<T>` on a set type (EF would discover it as a primitive collection), and **never** let `SetTypeRegistry` match by store-type name (`text[]` belongs to the provider's native `string[]` mapping). New set types are wired exclusively through `SetTypeRegistry.Register`
- **Value sets**: `Count`/`IsEmpty` must stay instance properties (extension properties cannot appear in expression trees — CS9296 — and would be untranslatable)
- **Value sets — a set type that normalizes or validates elements in `From` MUST also override `IValueSet<T>.NormalizeElement`** (and, on the EF side, pass that same function as the definition's `normalizeValue`). `Contains`/`Add`/`Remove` take a bare element, so without it the probe is compared un-normalized against normalized storage — a silently wrong answer client-side and a wrong bound parameter server-side
- **Value sets — a set type that overrides `CanonicalComparer` MUST also override `IValueSet<T>.CanonicalOrder` to return it.** `Contains`/`Add`/`Remove` binary-search the canonical array; searching with an order the array was not sorted by misses elements that are present
- **Value sets — a set type whose element type System.Text.Json cannot serialize as a scalar MUST override `IValueSetFactory<TSet,T>.ElementJsonConverter`.** JSON delegates elements to the serializer, which property-dumps an unknown type on write and yields `default` on read — silently, both legs. The hook is consulted last (only when `GetTypeInfo(typeof(T)).Kind != None`), so it never overrides a registered converter. The primitive-backed families are natively serializable and leave it `null`; the wrapper arities and the five NodaTime sets define one. Integer-backed wrappers write a JSON **number**, not a string, and decimal-backed ones a number keeping scale — the token type must always match the primitive the wrapper wraps. Byte-for-byte parity additionally holds for the string, Guid, integer and decimal arities; for the temporal and NodaTime ones the text differs (seven fraction digits, `+` escaped) while the value does not, which is asserted in `SetJsonConverterTests` rather than fixed
- **Value sets — a wrapper arity over a type whose default text form is lossy MUST pin a round-trip format**, in `FormatValue` *and* in its `SetTypeRegistry` bridge entry, and parse it strictly. `TimeOnly.ToString(null, invariant)` is `09:30` and `DateTime`'s is `06/15/2024 10:30:00` — an arity built like `Int32Set<T>` stores every temporal truncated to the second, and loses `DateTimeKind`, silently on the way to the column. The four temporal arities and the five NodaTime ones do this — since 9.0.0 the core `ParseValue` parses strictly too, not only the EF bridge; the string, Guid, integer and decimal ones correctly take the default
- **Value sets — canonical form in SQL is built by `ValueSetSqlGuard`, never by a translator.** For every family with `CanonicalizesInSql`, the translator emits `ValueSetSqlGuard.CanonicalUnion`/`CanonicalAdd`/`CanonicalIntersect`/`CanonicalExcept` and the guard's `CanonicalExpander` builds the subquery: it needs table aliases, and EF Core's alias pass (which runs after translation and before the guard) parses every alias as one letter and a number, while a translator has no `SqlAliasManager`. Keep `ORDER BY x, ordinality` with `DISTINCT ON`: it keeps the first copy of each value as `ValueSetCore` does (`1.0` vs `1.00`, `-0` vs `0`); a plain `DISTINCT` keeps any copy (seed `canonical-set-keeps-any-copy`). Drop NULL elements (`WHERE x IS NOT NULL`), and write the multiset form only where order and duplicates cannot change the answer. A family joins only if PostgreSQL orders its store type as the family's canonical comparer does; a wrapper arity relies on its element's `CompareTo` ordering as the primitive does (`docs/value-sets.md`). `CanonicalSetOperationParityTests` (integration) is the authority
- **Value sets — a text `Union` translates to `array_cat`, which does NOT canonicalize.** Only order- and multiplicity-insensitive operators may compose on it: `@>`, `<@`, `&&`, and the proper subset/superset pair written as `<@ AND NOT @>` for exactly that reason. Since 9.0.0 everything else is refused on the **final SQL tree** by `ValueSetSqlGuard`, run from a decorator around the provider's `IRelationalParameterBasedSqlProcessorFactory` (every query, `ExecuteUpdate` and `ExecuteDelete` passes through it). It **fails closed**: the translator emits the placeholder `ValueSetSqlGuard.UnguardedUnion` and only the guard renames it to `array_cat`, so a `ReplaceService` that drops the decorator makes every server-side `Union` fail on the server instead of silently skipping the refusals. Never emit `array_cat` directly, and never match it by name before the guard has run. It follows values *derived* from `array_cat` — through `array_remove` (which preserves canonical form rather than establishing it), `CASE`, `COALESCE` and subquery/set-operation columns — and allows them only under `@>`/`<@`/`&&`, `cardinality(…) = 0`, a null test, or in the outermost projection (materialization canonicalizes); equality, `cardinality`, `GROUP BY`, `DISTINCT`, `ORDER BY`, deduplicating set operations, `IN` and `UPDATE` setters throw. Never go back to recognizing these in LINQ: the 8.0.0 guard matched `==` inside a list of operators and a projection, a ternary, a coalesce, `GroupBy`, `Distinct` and `ExecuteUpdate` all translated and answered wrongly. `ValueSetsMemberTranslator` still *declines* `Count` over a visible union, which is what gives a projection its client fallback. The same guard refuses `to_jsonb(<value set>)` in an `UPDATE` setter — `ExecuteUpdate` of a value set inside a JSON column, which writes a JSON array where the document holds the literal, after which the row no longer loads — keyed off the translated setter, so a join or `EF.Property` cannot bypass it. `UnionCanonicalityTests` and `ExecuteUpdateJsonTests` (integration) assert results, not SQL. Do not "fix" text by sorting it in SQL: `ORDER BY` on `text` uses the database collation, not ordinal, so it would disagree with the client's canonical order — the same defect one layer down (#479 decides whether text moves to code point order and `COLLATE "C"`)
